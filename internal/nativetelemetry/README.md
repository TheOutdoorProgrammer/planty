# Native telemetry relay

`POST /v1/native-telemetry` reuses Planty's application bearer authentication. The version 1 JSON envelope contains numeric release/build identifiers and up to 16 static operation events. The handler rejects unknown fields and requests over 64 KiB, limits concurrent processing to two requests, and shares a 60-event burst with one event replenished per second. No device identifier, request URL, notification payload, error message, or arbitrary attributes enter the exported records.

Each event becomes a correlated OTLP trace and log for `planty-ios`, retaining its original timestamp and release/build. HTTP 204 follows successful protobuf acknowledgments from both collector endpoints. HTTP 503 or 429 leaves delivery with the client and supplies `Retry-After: 60`. Delivery is at least once: an interrupted request can repeat an accepted signal, and restarts do not preserve a deduplication cache. Replays reuse event-derived trace/span IDs. Collector acknowledgment relies on the configured collector's durable export queue; it does not prove final Grafana ingestion.

Set `OTEL_EXPORTER_OTLP_ENDPOINT` to the existing trusted HTTP/protobuf collector base endpoint. An absent endpoint or `OTEL_SDK_DISABLED=true` disables acceptance. Collector credentials are never obtained from the mobile request. The collector response is bounded and redirects and partial-success responses are rejected.

Clients can report actual queue loss after recovery using `telemetry.delivery`, outcome `failure`, and error class `queue_full` or `queue_expired`. These classes belong only to delivery events and carry no raw details. For API correlation, the client creates the event UUID before sending the request and propagates its full bytes as W3C trace ID, last eight bytes as span ID, and sampled flag `01` so the backend records the child span.

Crash and hang records contain one app image UUID, architecture, and up to 64 offsets relative to its `__TEXT` segment. The private object-store key is derived from validated UUID and architecture. Symbols must be a thin Mach-O dSYM with matching identity, valid DWARF, and a valid text range; universal files must be thinned before publication. LLVM's `llvm-symbolizer` adds the preferred text address to each offset and returns function, source basename, and line. Subprocess time and output are bounded, temporary files are private and removed, and raw tool errors are not exported. Missing or mismatched symbols retain the UUID and bounded relative offsets with `symbolication.status=unresolved`.

Trusted CI symbol publication uses a separate HTTP handler outside application bearer authentication. The app credential cannot authorize that handler. `InspectSymbols`, `ValidateSymbols`, and `SymbolKey` are shared by the publisher, upload handler, and resolver. The store's `Get` interface reuses existing photo storage without exposing symbol objects through photo URLs.

MetricKit reports the device architecture, so an arm64e report can use an arm64 app image with the exact same UUID. If fetching the arm64e object fails, including a deferred MinIO read error, the resolver closes that reader before trying arm64 within the original deadline. Each read is bounded to 64 MiB plus one overflow byte; successfully read objects with invalid identity or size are rejected without fallback.

Run `go test -race ./...` for schema, authentication, collector failure, and Mach-O fixture coverage. The real LLVM subprocess test runs when `llvm-symbolizer` is on PATH, or with `PLANTY_TEST_SYMBOLIZER_IMAGE` set to an image whose entrypoint is the symbolizer binary. See `testdata/README.md` for fixture provenance.
